# 調査メモ：詠唱から LLM でガチャ的に魔法が出る機能

- 調べた日：2026-11-22
- 目的：詠唱（自由な言葉）を LLM に通して、ビームの代わりに「炎の竜」のような透明なエフェクトが魔法陣から出る機能を足すとき、どう作るとよいかを調べる。
- 想定している機能：適当に考えた詠唱に「燃え盛れ」や竜を思わせる言葉が入っていたら、魔法陣から炎の竜の形をした透明なエフェクトが出て、ゲームのキャラクターのように動きながら的に当たる。何が出るかは、ガチャのように決まる。
- 調べ方：ウェブ検索とページの読み込み。LLM の呼び方と料金は、手元の Claude API リファレンスでも確かめた。
- 別に作っている「言葉から特殊な魔法陣を生成する」試作（セル・オートマトン）は、あとで合流させる前提。その中身は、この調査では見ていない。

## 印の意味

- 【確認】出典のページを取得し、その記述が載っていることを確かめた。
- 【手元資料】Claude Code に付属の Claude API リファレンス（2026-11-03 時点の写し）で確かめた。ウェブのページではない。
- 【抜粋】検索結果の抜粋に出ただけで、本文は読めていない。
- 【一般】広く知られていること、またはこちらの知識。今回はページで確かめていない。

【確認】の項目も、言い回しは要約している。そのまま引用するときは、原文で確かめること。

## 先に結論

1. **スマホの中の LLM は、まだ使えない。** Android の Chrome は、ブラウザ内蔵の LLM に未対応と、公式ページに書かれている。LLM を使うなら、小さな中継サーバーが要る。
2. **LLM には「選択肢から選ぶ」だけをさせる。** 属性・姿・動きを、決まった選択肢から選ばせる。レア度と強さは、コードで決める。これで、結果の安定、ガチャの抽選、「最強」と書くだけの攻略への対策、安全面が、まとめて片づく。
3. **生き物の形のエフェクトは、いまの描き方のまま作れる見込み。** 頭を動かし、鎖のように胴体を追従させ、光を重ねる。実機での速さは未確認。
4. **声の聞き取りが、いちばんの不確定要素。** 作った言葉や当て字を、どこまで正しく文字にできるかは、実機で試さないとわからない。
5. **はじめは LLM なし（辞書）で作り、面白いかを確かめるのが早い。** 中継サーバーも費用も要らない。

## 1. 先行例

- **1-1【確認】Infinite Craft**（2024 年。出典：Wikipedia）
  - 2 つの言葉を合成すると、LLM が新しい言葉と絵文字を作る。
  - 合成のたびに、データベースに既出かを調べる。同じ組み合わせは、全員に、いつも同じ結果が出る。
  - 最初に見つけた人には「First Discovery」と表示される。
  - 不適切な結果を除くフィルタがある。たまに出る支離滅裂な結果は、むしろ面白がられている。
  - 利用が増えて、サーバーが過負荷になった。
- **1-2【確認】研究「Real-Time World Crafting」**（2025 年。出典：arXiv）
  - プレイヤーの文章を、LLM が決まった書式のデータに訳す。ゲーム側は、それを検査してから使う。
  - 軽い誤りは、既定の値で補う。まったく使えないときは、害のない「不発」の演出にする。
  - 生成にかかった時間は、いちばん速いモデルで平均 3.35 秒、いちばん遅いモデルで 12.2 秒。速いモデルほど、質が低かった。
  - 試したのは素直な入力だけ。製品にするなら入力の検査がもっと要る、と書いている。
- **1-3【確認】研究「SpellForger」**（2025 年。出典：arXiv）
  - 自由な文章から、小さな言語モデル（BERT）で、呪文の型や性質を決める。端末の中だけで動き、平均で約 0.2 秒。
  - 生成された値は、そのまま使わない。決めておいた範囲に当てはめ直す（調整の主導権を、作り手に残すため）。
- **1-4【確認】Mage Arena**（2025 年 7 月に早期アクセス開始。出典：Wikipedia）
  - 声で呪文（Fireball、Freeze、Magic Missiles など）を撃つ対戦ゲーム。
  - 最初の週に、同時に 1.6 万人超が遊んだ。動画サイトで広まったのが大きい。
- **1-5【確認】In Verbis Virtus**（出典：Wikipedia）
  - マイクに向かって、ゲームのために作られた架空の言語の呪文を、実際に唱える。
- **1-6【確認】AI Spelcraft**（2025 年 8 月発売。出典：Steam のストアページ）
  - 漢字で呪文を作ると、AI がダメージと効果を決める対戦ゲーム。
- **1-7【確認】詠唱の約束事の例**（出典：Wikipedia「BLEACH」）
  - 詠唱を省いて撃つ「詠唱破棄」は、威力が落ちる。
  - 2 つの詠唱を並行する「二重詠唱」、撃ったあとに詠唱して威力を補う「後述詠唱」もある。
- **1-8【一般】**
  - Scribblenauts：同じ言葉を使い回せない上級モードで、万能な単語への偏りを抑えた。
  - Magicka、Noita：組み合わせの発見と、自爆の危険が、面白さの芯。

**まとめ**

- うまくいっている例は、LLM を「訳す役」か「判定する役」に限っている。結果を保存して、同じ入力には同じ結果を返している。
- 声で撃つ例（1-4、1-5）は、どちらも決まった呪文で、自由な詠唱ではない。「自由な詠唱 × 声」は、先行例が少ない。

## 2. 詠唱を、演出の指定に変える

- **2-1【確認】形を先に決め、LLM には訳すだけをさせる。** 受ける側は「検査する → 既定の値で補う → 不発にする」の 3 段で受ける。（1-2、1-3 に共通する形）
- **2-2【手元資料】Claude API には、答えの形を縛る機能がある**（構造化出力）。
  - 決めた形どおりの JSON が返る。
  - 選択肢の列挙は使える。数値の上限・下限や、文字数の制約は使えない。
  - 初めて使う形は、最初の 1 回だけ準備の時間がかかる。その後 24 時間は保存される。
  - 安全上の理由で断られた場合は、形に合わない答えが返ることがある。
- **2-3【確認】Chrome 内蔵の LLM にも、同じように形を縛る指定がある。**（出典：Chrome の公式ページ）
- **2-4【手元資料】いまの Claude のモデルは、答えのゆらぎを決める設定（temperature など）を変えられない。** 「設定で毎回同じ答えにする」ことはできないので、結果を保存して、同じ答えを返す。

ここから下は、調べたことをもとにした設計上の判断。

- **2-5 同じ詠唱に、同じ結果を返す方法**
  - 詠唱を整える（全角・半角の統一、空白と記号の除去）。
  - 整えた詠唱から、決まった計算で短い値（ハッシュ）を作る。それを鍵にして、結果を保存する。
  - 見た目の細部は、その値を「種」にした乱数で決める。同じ詠唱なら、同じ姿になる。
  - 声の入力は、同じ発声でも漢字の表記が揺れる。完全な一致は期待しない。
- **2-6 ガチャとの両立**
  - 「何が出るか（属性・姿・動き）」は、詠唱ごとに固定する。
  - 「レア度」は、撃つたびにコードで抽選する。
  - LLM には、レア度も威力の数値も出させない（1-3 の「生成された値をそのまま使わない」と同じ考え）。
  - LLM には「詠唱の出来」を 4 段階で返させる。抽選の確率を少し動かす材料にだけ使う。
- **2-7 「最強」と書くだけの攻略への対策**
  - 強さは、LLM が決めない。
  - 強さの総量はレア度で決め、速さ・大きさ・追尾に振り分けるだけにする。
  - LLM には「強さの自称（最強、無敵、必中）は評価に入れず、情景の具体さとまとまりだけを見る」と指示する。
  - 同じ詠唱の連発は、効果を落とす。
  - 的に属性の相性を持たせ、万能な答えをなくす。
  - 長い詠唱は時間がかかる、という代償を残す（1-7）。

## 3. ガチャの見せ方

- **3-1【確認】天井の仕組み。** 一定の回数を超えると確率を少しずつ上げる方式と、上限の回数で必ず高いレアを出す方式がある。（出典：Wikipedia「Gacha game」）
- **3-2【確認】魅力と批判。** 魅力は、不確かさと、報酬への期待から来ると説明されている。批判されているのは、レアを一瞬見せてから外す「ニアミス」の演出。（同上）
- **3-3【確認】色の慣習。** 低いレアは寒色で静か、中は暖色、最高は金や虹、または画面を覆うほどの光。結果が出る前の一瞬に、光や輪の「色」で兆しを見せる。この色の約束は、多くのゲームで共通している。（出典：HostedGG の記事）
- **3-4【一般】気持ちよさの要素。**
  - 自分の操作（タップや声）で始まる。
  - 「溜め → 兆し → 公開」の 3 拍。
  - 兆しは、色・音の高さ・振動を同時に変える。
  - 途中で格上げされる「昇格」の演出（青から金へ）。
  - 低いレアは短く、高いレアだけ長く。

この試作への当てはめ（提案）。

- 魔法陣が、抽選機を兼ねる。線の色・輪の数・音の高さを、兆しに使う。
- まれに、陣が割れて金色で描き直される「昇格」を入れる。
- だます演出（ニアミス）は入れない。

**法律面**

- お金を扱わない間は、ガチャの規制の対象にならない見込み【一般】。
- 日本では、決まった組をそろえると景品が出る方式（コンプガチャ）が、2012 年に違法とされた【確認】（出典：3-1 と同じ）。
- 課金を入れることになったら、その時点で調べ直す。

## 4. 生き物の形をした、透明なエフェクト

- **4-1【確認】鎖で胴体を作る方法。** 点を「前の点から一定の距離」に引き戻す。これを頭から順にくり返すだけで、頭についていく胴体になる。（出典：Constraints の解説ページ）
- **4-2【一般】すすめる作り方（いまの描き方のまま）。**
  - 頭 1 点を、舵を切るように動かす。
  - 20〜40 個の節の鎖を、頭に追従させる。
  - 節ごとに、にじんだ光を重ねる（いまのビームや光の粒と同じ部品）。
  - 頭にだけ、線で描いた輪郭（竜・鳥・狼）を重ねる。
  - 翼やひれは、胴の節に短い鎖を付ける。
- **4-3【一般】動きの型。**
  - 追尾：曲がれる速さに上限をつけて、的へ向かう。
  - 蛇行：進む向きと直角に、波を足す。
  - らせん：的のまわりを回りながら、半径を縮める。
  - 旋回してから突撃：「現れる → 回る → 突っこむ」を、順に切り替える。
- **4-4【一般】群れ（鳥・蝶・魚）。** 「離れる・そろえる・集まる」の 3 つの規則で動かす方法が定番。
- **4-5【一般】もっと凝った描き方（WebGL のシェーダー）。** 見栄えはよいが、画面全体で使うと、中くらいの性能のスマホには重い。使うなら、小さな範囲に限る。

**速さの見込み**

- 鎖 1〜3 体と、光の重ね描き数百個は、いまの描き方で動く見込み【一般】。実機で測る必要がある。
- 発射の場面は、いまでも描くものが多い。生き物を出すときは、ほかの要素を減らして釣り合いを取る。

**いまの試作とのつながり**

- 生き物が的へ飛ぶには、エフェクトを空間に固定する仕組みが先に要る。いまのビームは、いつも画面の中央へ飛ぶ。（[演出の調査メモ](charge-fire-research.md)の B5）
- 透けたものは、逆光と余白で読ませる。カメラ映像を少し暗くする工夫は、生き物の見やすさにも効く。（[演出の調査メモ](charge-fire-research.md)の A1）

## 5. 公開ページから LLM を呼ぶ

- **5-1【一般】鍵を、ページに置けない。**
  - 公開ページのプログラムに入れた鍵は、誰でも読める。
  - 小さな中継サーバーに鍵を置き、ページからは詠唱の文字だけを送る。
  - 中継の側で、文字数の上限、回数の制限、1 日の上限、結果の保存を行う。
- **5-2【確認】Android の Chrome は、ブラウザ内蔵の LLM に未対応。**
  - 公式ページ（2026-10-21 更新）に、Android・iOS の Chrome は未対応と書かれている。
  - 対応しているのは、パソコン（Windows・Mac・Linux）と、一部の Chromebook。空き容量 22 GB 以上などの条件がある。
  - 開発者向けの告知（2026 年 4 月）には、Android 版は試作中で、最初の公開のあとに出す、とある。時期は書かれていない。
  - （出典：Chrome の公式ページ、Chromium の開発者向け掲示）
- **5-3【確認】スマホのブラウザの中で、小さなモデルを動かす方法もある**（Transformers.js など）。ただし、GPU を使う機能（WebGPU）は「多くのブラウザでまだ実験的」と、公式の説明にある。Android の Chrome は、WebGPU に版 121 から対応している。（出典：Hugging Face の公式ページ、MDN の対応表）
- **5-4【一般】スマホの中で LLM を丸ごと動かす方法**は、モデルが数百 MB〜数 GB ある。中くらいの性能の機種では厳しい。今回はすすめない。

**待ち時間**

- 【確認】別の研究では、もっと大きな出力で 3〜12 秒かかっている（1-2）。
- 今回は、選択肢を選ぶだけの小さな答えなので、もっと短い見込み。ただし、測っていない。
- 【手元資料】待ち時間を縮めるには、考える深さの設定を低くする。小型のモデル（Claude Haiku 5.5）は、考える過程を切ることもできる。

**待ち時間の隠し方**（提案）

- 詠唱している間を、そのまま溜めにする。聞き取りの途中経過から辞書で言葉を拾い、陣の色や形を先に変えていく。
- 詠唱が確定したら、すぐ LLM に送る。
- レア度はコードで即決できるので、色の兆しは LLM を待たずに出す。姿の公開だけ、LLM の答えを待つ。
- 2.5 秒たっても届かなければ、辞書の結果で撃つ。遅れて届いた答えは保存して、次から使う。
- 同じ詠唱は、端末に保存した結果で、すぐ出す。

**LLM を使わない予備（辞書）**【一般】

- 漢字と語幹で引く。例：「燃・炎・焔・紅蓮」は火、「竜・龍・ドラゴン」は竜、「凍・氷・雪」は氷、「雷・稲妻・轟」は雷。
- 日本語は漢字が意味を運ぶので、単純な辞書でも、かなり当たる。
- どれにも当たらない詠唱は、ハッシュから型を決める。

## 6. 声の入力

- **6-1【確認】音声がどこで処理されるかは、ブラウザが決める。** サーバーに送られることも、端末の中で処理されることもある。（出典：MDN）
- **6-2【確認】Android の Chrome の対応状況。**（出典：MDN の対応表）
  - 音声認識そのものは、使える。途中経過を受け取ることもできる。
  - 「端末の中で処理する」指定は、未対応。
  - 「この言葉を優先して聞き取る」指定も、未対応。
  - 「続けて聞き取る」設定は、設定できるが効かない。

ここから言えること。

- 音声は、サーバーに送られうる。その前提で、ページに一言書く。
- 1 回の聞き取りで 1 つの発話なので、詠唱は「ひと息」で言える長さにする。
- 作った言葉を優先して聞き取らせることは、できない。

未確認のこと【一般】。

- 日本語の聞き取りの癖。作った言葉や当て字は、近い実在の言葉に直される。読みがなは取れない。間が空くと、そこで終わる。
- いまの「声の大きさで発射」と同時に使うと、マイクの取り合いになることがある。

代わりの入力。

- 文字の入力欄（いつでも使える。当て字の遊びに強い）。
- キーボードの音声入力で、入力欄に入れる（聞き間違いを直してから撃てる）。

## 7. 安全面

- **7-1【一般】答えが選択肢だけなら、悪意のある詠唱で起きるのは「選ばれる値が変わる」まで。** 画面に好きな文を出させる道がない。
- **7-2 守る線は 3 つ**（設計上の判断）
  - レア度と強さを、LLM に決めさせない（詠唱に「レア度を最高にせよ」と書かれても効かない）。
  - LLM の答えは、中継の側と端末の側の両方で、選択肢の一覧と照らす。外れたら、既定の値にする。
  - 自由な文の欄（呪文の名前や説明文）を作らない。名前が欲しければ、選ばれた値から、決まった語を組み立てる（例：「紅蓮」と「竜」）。
- **7-3【確認】意味をなさない入力・使えない入力は、「不発」にする先例がある**（1-2）。しぼむ煙のような演出にすれば、罰ではなく遊びになる。
- **7-4【手元資料】LLM に断られた場合は、決めた形に合わない答えが返ることがある**（2-2）。そのときは、辞書に切り替える。
- **7-5【確認】結果をほかの人と共有する機能を入れると、話が変わる。** 全員に結果が見えるゲームは、フィルタを持っている（1-1）。自分の入力が自分に見えるだけの間は、当面不要。
- **7-6【一般】費用の悪用**は、中継の回数制限と 1 日の上限で止める。上限に達しても、辞書で動き続ける。
- **7-7 プライバシー。** 詠唱の文字は、中継と LLM の事業者に送られる。音声は、ブラウザの判断でサーバーに送られうる（6-1）。その旨を、ページに書く。

## 8. 設計の案

### 流れ

1. **入力**：声（音声認識）か文字。確定した文字列を受け取る。
2. **整える**：全角・半角の統一、空白と記号の除去、長さの上限（60 字ほど）。ハッシュを作る。
3. **端末ですぐ行う**：辞書で仮の解釈を作る。レア度を抽選する。装填の演出を始める。
4. **並行して行う**：端末に保存した結果を引く。なければ、中継に詠唱を送る（2.5 秒で打ち切り）。
5. **中継**：長さ・回数・1 日の上限を確かめる。保存した結果を引く。なければ LLM を呼び、答えを選択肢の一覧と照らして保存し、返す。
6. **端末で合わせる**：LLM の解釈、コードが決めたレア度、ハッシュから作った種を合わせて、描く指定にする。
7. **見せる順**：色の兆し → 姿の公開 → 生き物の動き → 命中。

### LLM に返させるもの

すべて、決まった選択肢から選ばせる。

| 項目 | 意味 | 選択肢の例 |
|---|---|---|
| element | 属性 | 火、氷、雷、風、水、土、光、闇 |
| form | 姿 | 竜、蛇、鳥、狼、魚、群れ、刃、玉 |
| motion | 動き | 追尾、蛇行、らせん、旋回してから突撃、ジグザグ、突進 |
| temper | 気配 | 荒々しい、静か、おどけた、厳か、不気味 |
| craft | 詠唱の出来 | ふつう、まずまず、よい、見事 |
| flag | 扱い | 問題なし、意味をなさない、不適切 |

コードが決めるもの。

- レア度、乱数の種、大きさ、速さ、節の数、体の数。
- 色（属性とレア度の表から）。
- 詠唱の長さの区分（完全な詠唱・短縮・名前だけ）。

### レア度と乱数を決める場所

- レア度は、端末のコードで、撃つたびに抽選する。お金も対戦もないので、サーバーで決める必要はない。
- 基本の確率に、次の補正をかける。数値は、遊んで調整して決める。
  - 詠唱の出来（craft）が高いと、少し上がる。
  - 完全な詠唱で少し上がり、名前だけだと下がる（1-7 の約束事）。
  - 同じ詠唱の連発で下がる。
  - 高いレアが出ない回数が続くと、少しずつ上がる（3-1 の天井）。
- 姿の細部は、ハッシュを種にした乱数で決める（同じ詠唱は、同じ姿）。飛ぶ道筋の細部は、毎回の乱数で決める。

別の案：レア度も詠唱ごとに固定にすると、「当たりの詠唱を探す」発見型の遊びになる（1-1 の型）。ガチャらしさを取るなら、「撃つたびに抽選」。

### どこで何を動かすか

| 場所 | 受け持つこと |
|---|---|
| 端末（ページ） | 入力、音声認識の呼び出し、詠唱を整える、辞書、レア度、描画、音、結果の保存 |
| 中継サーバー | 鍵の保管、LLM の呼び出し、結果の保存、回数と総量の制限 |
| LLM | 解釈だけ |

いまの試作は「1 枚の HTML で、外部の読み込みなし」。中継を呼ぶと、初めてこれが崩れる。辞書だけでも遊べる形を保てば、通信なしで動く性質は残せる。

### LLM のモデルと費用の目安

Claude を使う場合の候補【手元資料】。料金は 100 万トークンあたりで、2026-11-03 時点の写し。決める前に、公式の料金ページで確かめること。

| モデル | 入力 | 出力 | 向き |
|---|---|---|---|
| Claude Opus 5.5 | 4 ドル | 20 ドル | 既定の候補。解釈の質を優先 |
| Claude Haiku 5.5 | 0.10 ドル | 0.50 ドル | いちばん安い。費用と待ち時間を優先 |

- 概算：1,000 回の詠唱で、Haiku 5.5 は約 0.14 ドル、Opus 5.5 は約 5.6 ドル。1 回あたり入力 650・出力 150 トークンと仮定した。考える過程の分は含めていない。
- Opus 5.5 は考える過程を切れないので、上の概算より多くかかる。Haiku 5.5 は切れる。
- 同じ詠唱は保存した結果を返すので、実際の回数はもっと減る。
- どちらにするかは、実際の詠唱 30 個ほどで、解釈の質と待ち時間を比べて決めるのがよい。
- 設計そのものは、ほかの事業者の LLM でも、同じ形で作れる。

### 予備（辞書）

通信なし・時間切れ・上限超え・LLM に断られた、のどの場合も、辞書の結果で撃つ。辞書にも当たらなければ、ハッシュから型を決める。「撃てない」状態を作らない。

## 9. 進め方（3 段階）

1. **最小（サーバーなし、1 枚の HTML のまま）**
   - 文字の入力欄と辞書。ハッシュの種。
   - 鎖の生き物 1 種（竜か蛇）と、動き 2 種（追尾・蛇行）。
   - レア度の抽選と、魔法陣の色の兆し。
   - 実機で、動きの重さ（コマ落ち）を測る。
   - 実機で、声の聞き取りを試す（作った詠唱が、どのくらい正しく文字になるか）。
   - ここで「面白いか」を確かめる。
2. **LLM をつなぐ**
   - 中継サーバー、結果の保存、回数の制限、選択肢だけの答え、時間切れの予備。
   - 姿（鳥・狼・群れ）と、動き（らせん・旋回してから突撃）の追加。
   - 天井。詠唱の約束事（完全な詠唱・詠唱破棄・後述詠唱）。
3. **全部**
   - セル・オートマトンの魔法陣の試作を合流させる。同じ種から、陣と生き物の模様をそろえる。
   - 出した組み合わせの図鑑。連発の減衰。音の使い分け。
   - Android の Chrome が内蔵の LLM に対応したら、そちらを使う切り替え。

## 10. 決めてほしいこと

1. まず辞書だけ（段階 1）で試すか、はじめから LLM をつなぐか。おすすめは、段階 1 から。
2. LLM をつなぐとき、中継サーバーをどこに置くか。どの LLM の、どのモデルを使うか。アカウントと費用が関わる。
3. レア度は「撃つたびに抽選」か、「詠唱ごとに固定」か。
4. 入力は、声を主にするか、文字を主にするか。
5. セル・オートマトンの魔法陣の試作を、いつ合流させるか。合流には、そのコードが要る。

## 11. 調べきれなかったこと

- 詠唱の約束事の出典は、Wikipedia の 1 作品だけ。ほかの作品の約束事は確かめていない。
- ガチャの演出を、ゲームの作り手自身が解説した記事。本文が開けなかった。
- 声で撃つゲーム（1-4、1-5）で、聞き間違いがどう扱われているか。作り手の振り返りは見つからなかった。
- Android 版の内蔵 LLM の時期。「試作中」（2026 年 4 月）より新しい公式の情報は、見つけていない。
- Android の Chrome の音声認識で、音声が実際にどこで処理されるか。「ブラウザが決める」としか書かれていない。
- 中継サーバーのサービス（Cloudflare Workers など）の無料枠と、回数制限の機能の詳細。
- 次の 4 つは、実機か、実際の呼び出しで測る必要がある。
  - 今回の形での LLM の待ち時間。
  - 声の聞き取りの精度。
  - 「声の大きさで発射」と音声認識を、同時に使えるか。
  - 鎖の生き物の描画の重さ。
